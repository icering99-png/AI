## 4. Как работать: ежедневный контур

### 4.1 Микроритм git (вместо ваших 10 гейтов на каждый чих)

- **Коммит = 1 намерение.** Сделали одну осмысленную вещь → `git commit -m "feat: add build_mirror script"`. Не копите.
- **Ветка на задачу** (`git switch -c fix-manifest`), в `master` — только работающее.
- **Сообщение отвечает «почему»**, а диф отвечает «что». Conventional Commits.
- **`git reflog` — страховка.** «Потеряли» коммит — он почти всегда recoverable. Страх ошибки уходит — скорость растёт.
- **Push в удалённый репозиторий ежедневно** (GitHub приватный — бесплатно). Это ваш настоящий Backup до всяких Golden.

### 4.2 Формула задачи для ИИ-агента (Antigravity/Gemini)

Любую задачу агенту формулируйте четырьмя блоками — это сжатие лучшего из вашего AGENTS.md:

```
ЦЕЛЬ: что должно получиться (одним предложением, измеримо)
ОГРАНИЧЕНИЯ: файлы/пути, что не трогать, лимиты
КРИТЕРИЙ ГОТОВНОСТИ: какая команда должна выйти зелёной
КОНТЕКСТ: 2–3 ссылки на файлы, не больше
```

Пример: «ЦЕЛЬ: state_manifest содержит все модули core/. ОГРАНИЧЕНИЯ: только scripts/build_manifest.py. КРИТЕРИЙ: python scripts/build_manifest.py && python -m unittest discover -s tests — зелёный. КОНТЕКСТ: state_manifest.json, core/.»

### 4.3 Как проверять агента (не верификационный театр)

1. **Слова агента — не доказательство.** Только: сырой вывод команды, диф, зелёные тесты.
2. **Просите диф, а не пересказ:** «покажи git diff».
3. **Тест — первый критик, LLM-критик — второй.** Детерминированный оракул дешевле и честнее консилиума из шести субагентов (см. Zheng 2023 про ошибки LLM-судей).
4. **Одна сессия = одна задача.** Разрослась — закройте с фиксацией в HANDOFF (коротком!) и начните новую.

### 4.4 Баланс продукт/процесс — правило 60/20/20

- **60% времени — продукт** (devops_quest, реальные фичи).
- **20% — тесты и качество.**
- **20% — инфраструктура и правила.**
- Мета-работа (новые гейты, регламенты) — только по триггеру боли: случилась реальная ошибка → запись в failure_index → правило. Не наоборот. Ваши CLAIM-0007/0008 сами об этом: 94% проблем от лишнего вмешательства.

### 4.5 Definition of Done (чек-лист перед «готово»)

- [ ] `python -m unittest discover -s tests` — зелёный
- [ ] Изменения закоммичены, сообщение объясняет «почему»
- [ ] Если менялось поведение — тест обновлён ДО сдачи
- [ ] HANDOFF (≤50 строк) отражает новое состояние

## 6. Антипаттерны (выучить по именам, все найдены в этом проекте)

1. **Process-for-process** — правила строятся для правил; метрика ADR растёт, продукта нет.
2. **Ручные зеркала** — две копии одного текста = будущий дрейф. Копия допустима только как артефакт сборки.
3. **Неверифицируемая метрика** — «27 модулей Zero Drift» в файле с 1 записью. Любая метрика должна пересчитываться скриптом.
4. **Правило-невыполнимка** — ident ≤ 15 нарушается собственным кодом; одно такое правило обесценивает десять рабочих.
5. **Validation theater** — зелёная галочка без сырого вывода; консенсус шести агентов без детерминированного оракула.
6. **Сжигание контекста обязаловкой** — 455 строк HANDOFF на каждый bootstrap (см. Lost in the Middle).
7. **Церемония вместо барьера** — гейт, существующий только как текст промпта, — не барьер. Барьер = то, что физически падает (тест, хук, CI).

## 7. Мини-словарь

- **ADR** (Architecture Decision Record) — короткая запись решения: контекст → выбор → последствия.
- **CI** (Continuous Integration) — автоматическая проверка каждого push (тесты, линтер).
- **DAG** — направленный граф без циклов; у вас — последовательность шагов с зависимостями.
- **DORA-метрики** — частота деплоя, lead time, MTTR, доля неудачных изменений.
- **Golden test** — тест-инвариант, фиксирующий поведение, которое нельзя сломать.
- **Mutation testing** — проверка тестов: в код вносятся мутации; хорошие тесты их ловят.
- **Postmortem (blameless)** — разбор инцидента с фокусом на первопричине, а не виновном.
- **Strangler Fig** — постепенная замена системы: новое растёт вокруг старого, пока старое не отомрёт.
- **Validation theater** — имитация проверки (галочки, консенсусы) без сырых доказательств.

## 8. Видение: универсальный эталон «закинул в Gemini — работает»

Цель: один пакет, который копируется в проект и подстраивается под домен (кодинг / игры / 3D) подключением весов. Правильная архитектура — **не один гигантский промпт на всё, а тонкое ядро + сменные профили + реестр моделей**:

```text
ЭТАЛОН (инвариант, всегда одно и то же)
├── AGENTS.md                    — 4 обязательных гейта (после FIX-07)
├── core/                        — детерминированные гварды (AST, пути, диффы)
├── failure_index.json (v2)      — память ошибок: домен + детекция + регрессионный тест
├── schemas/model_registry.json  — РЕЕСТР: домен → веса → оракул → allowed_paths
├── rules/profiles/              — СМЕННАЯ ЧАСТЬ (знание домена)
│   ├── CODING.md                — оракул: unittest/pytest
│   ├── GAME.md                  — оракул: скрипт самопроверки игры
│   ├── THREED.md                — оракул: bpy headless + glTF-валидатор
│   └── MODDING.md               — оракул: валидатор модов + smoke-запуск игры
└── assets/defects/              — ГАЛЕРЕЯ ДЕФЕКТОВ: известные-плохие фикстуры,
                                     которые оракулы обязаны отклонять
```

Четыре принципа:

1. **Универсален контракт, а не контент.** Ядро не знает про 3D и игры — оно знает про «план → APPROVE → детерминированный оракул → память». Всё доменное — в профилях, подгружаемых по триггеру (ваш же Progressive Disclosure Navigator, расширенный на домены). История проекта это подтверждает: ADR-001 когда-то правильно вырезал 3D/CAD из ядра — возвращать его нужно профилем, а не обратно в конституцию.
2. **Каждому домену — свой детерминированный оракул.** Кодинг: exit_code тестов. Игры: самопроверка скриптом (например, node-скрипт, валидирующий структуру данных викторины). 3D: `blender --background --python check_scene.py` + glTF-Validator. Домен без оракула не считается готовым — прямое следствие ваших CLAIM-0001/0002: самокоррекция без внешнего оракула деградирует.
3. **Реестр моделей — данные, не код.** Один JSON: домен → локальный вес (Ollama) → fallback-цепочка → облачная эскалация → оракул. Смена весов = правка JSON, не правка ядра. Честность о возможном: модели 1.5b–7b хороши для классификации, перевода и мелких правок; генерация реального 3D-кода и крупных рефакторингов требует старших моделей — реестр должен это отражать, а не скрывать.
4. **Портативность проверяется, а не заявляется.** E2E-тест (FIX-13): копия шаблона в чистой папке поднимается и проходит тесты без ручных шагов. Плюс тонкие адаптеры под IDE (`.gemini/`, `AGENTS.md`, `CLAUDE.md`), генерируемые скриптом зеркал, — руками их больше не правим.

Порядок внедрения: FIX-07 (худеем до 4 гейтов) → FIX-10 (реестр) → FIX-11 (профили, начиная с CODING) → FIX-12 (3D-оракул) → FIX-13 (e2e). Делать все профили сразу — повторение ошибки «процесс ради процесса»: CODING готов на 90%, THREED — следующая ступень (потребуется выучить bpy и 3D-математику), GAME вырастет из devops_quest.

## 9. Контур самоулучшения: «на те же ошибки — никогда»

Для 3D и моддинга повторяемость ошибок — главный убийца времени: мод после патча игры «молча» ломается, сцена экспортируется с вывернутыми нормалями, порядок загрузки конфликтует, а модель не помнит прошлую сессию. Поэтому эталону нужен замкнутый контур:

```text
ОШИБКА
  → 1. ЛОВЛЯ:    оракул упал (тест / check_scene.py / валидатор модов)
  → 2. ЗАПИСЬ:   failure_index v2: симптом, первопричина (5 почему), домен,
                 как детектировано, ЧТО ТЕПЕРЬ ЛОВИТ ЭТО АВТОМАТИЧЕСКИ
  → 3. ЛОВУШКА:  ошибка становится материальной: регрессионный тест
                 или файл в assets/defects/ (галерея известного-плохого)
  → 4. УРОК:     одно предложение в профиль домена (THREED.md / MODDING.md)
  → 5. ЗАКРЫТИЕ: только когда ловушка зелёно ловит воспроизведение
```

Три правила контура:

1. **Инвариант анти-дежавю: ошибка закрыта только тогда, когда её автоматически ловит оракул.** Запись в failure_index без привязки к тесту/фикстуре — это дневник, а не память. Проверяется скриптом: каждый `RESOLVED` обязан иметь зелёный регрессионный тест (FIX-14).
2. **Память растёт автоматически, правила меняются только через шлюз.** Агент свободно добавляет факты (записи об ошибках, фикстуры), но правка правил профилей — только через Candidate → Golden с APPROVE и проверкой хешей в CI. Ваш R002 (Oracle Immutability) уже даёт каркас, а CLAIM-0007 (94% проблем от ошибочного фидбека) — прямой аргумент за шлюз: само-правка правил — это самокоррекция без оракула, тот самый деградирующий случай из CLAIM-0001.
3. **В 3D и моддинге ловушки — материальные.** Не «старайся не переворачивать нормали», а фикстура `assets/defects/flipped_normals.blend`, которую `check_scene.py` обязан отклонить. Не «проверяй конфликты модов», а пара конфликтующих тестовых модов в фикстурах, которые валидатор обязан пометить. Урок, который можно уронить командой в CI, — единственный, который не забудется.

Ритуал синтеза (раз в неделю, 15 минут): `scripts/review_failures.py` выводит ошибки без ловушек и повторяющиеся симптомы → по каждой решается: новая фикстура, новое правило (через шлюз) или уже покрыто. Это конвейер «опыт → оракулы», не полагающийся на память модели между сессиями.

## 10. Заточка под Antigravity: эталон ↔ IDE

Главный принцип: **критичное живёт в файлах и CI, Antigravity — интерфейс, а не хранилище истины.** IDE молодая и меняется быстро; оракулы, реестр моделей и галерея дефектов обязаны работать и без неё — в терминале и CI. Тогда обновление Antigravity — не событие для эталона. (Урок из вашей же истории: захардкоженный `view_file` в «универсальном» регламенте — пример лишней привязки.)

| Слой эталона | Механизм Antigravity | Комментарий |
| :--- | :--- | :--- |
| AGENTS.md (L0) | Читается из корня воркспейса нативно | Держите тонким: 4 гейта + навигатор; детали — в `rules/` и профилях |
| Правила и профили | Глобальные правила `~/.gemini/antigravity/rules/` (генерируются `build_mirror.py`) | Воркспейс-специфика — только в AGENTS.md проекта, без дублей |
| Gate 1 RO-Lock | `.agents/hooks.json` PreToolUse → `pre_tool_guard.py` | Единственный физический барьер; доказательство срабатывания — FIX-06 |
| Gate 4 Proof of Work | Терминал Antigravity: raw stdout, exit_code | Доказательство — только из терминала, не из пересказа агента |
| Критик «pro» | Выбор модели в UI: старшая Gemini — ревью/архитектура; Flash — рутина/классификация; Ollama — перевод и мелочи | Имена моделей в UI меняются — таблица ролей живёт в `docs/ANTIGRAVITY_SETUP.md` (FIX-17), в реестре только идентификаторы |
| Оракул GAME | Браузер Antigravity — интерактивная проверка; Playwright — тот же сценарий в CI (FIX-18) | В сессии — браузер IDE, в CI — без IDE |
| Память L2 | `failure_index.json` — канон; панель Knowledge — витрина с краткими строками `FAIL-ID: симптом → ловушка` (FIX-19) | Knowledge живёт в IDE, не в git и не проверяется CI — только дополнение |
| 3D | Headless Blender в терминале; артефакты-рендеры — визуальный чек для человека | exit_code — для гейта, скриншот — для вас |

Первая фраза новой сессии (шаблон, хранить в `docs/ANTIGRAVITY_SETUP.md`):

> Работай по AGENTS.md. Прочитай HANDOFF.md, DECISIONS.md, failure_index.json. До `APPROVE <PLAN-ID>` — Read-Only. Успех = зелёный оракул в терминале (raw stdout, exit_code 0), не пересказ.

Гигиена контекста в Antigravity: HANDOFF ≤ 50 строк (иначе каждый запуск жжёт окно контекста — см. Lost in the Middle); экспорты истории чата не подгружать в сессию; скриншоты и артефакты — точечно, по одному на проверку, а не простынями.
