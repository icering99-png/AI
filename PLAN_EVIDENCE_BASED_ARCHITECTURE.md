# АРХИТЕКТУРА И ГЕНЕРАЛЬНЫЙ ПЛАН СИСТЕМЫ «ЭТАЛОН ИИ»
> **Оркестратор:** Antigravity  
> **Контур исполнения:** Local-First (Детерминизм + Локальные состязательные агенты)  
> **Внешний арбитр:** Gemini (Экономная эскалация микро-пакетами $\le 300$ симв. + режим глубоких вычислений)  
> **Инвариант управления:** Строгая доказательная база (Traceability Model) & Fail-Closed

---

## 1. Архитектурная модель доказательности (Traceability Model)

Система управляется сквозной 7-уровневой цепочкой происхождения:

```text
SOURCE (SRC-00XX: Академические статьи, стандарты NIST/NASA/W3C/OPA)
  │
  ▼
CLAIM (CLAIM-00XX: Фактологическая выжимка, численный результат, статус)
  │
  ▼
RULE (R-00XX: Формализованное инженерное правило, derived_from)
  │
  ▼
POLICY (Executable Rego / Python Middleware / AST Checkers)
  │
  ▼
GATE (Enforcement Points 1-10: if not gate.verify(): BLOCK())
  │
  ▼
EVIDENCE (Машиночитаемая аттестация: in-toto / PROV JSON, exit_code: 0)
  │
  ▼
STATE (Фиксация состояния: Candidate -> Backup -> Golden)
```

## 2. Двухосевая маршрутизация нагрузки (Cost Router vs Trust Router)

Система принимает решения по двум независимым ортогональным осям, где **Cost Router применяется первым**:

```text
                              ОСЬ ВЫЧИСЛЕНИЙ (Cost Router)
                          Легковесная ←────────────→ Тяжелая
                              │                          │
                              ▼                          ▼
                         TIER 0 / 1                 TIER 2 (Local Heavy)
                     (AST / Regex / Схемы)        (Local GPU/CPU Compute)
                              │                          │
                              └───────────┬──────────────┘
                                          │
                        ОСЬ ДОВЕРИЯ (Trust Router)
                     Хватает локального ума? 
                                ├── ДА ──► Локальное применение + RAW
                                └── НЕТ (Тупик / Спор > 2 раз)
                                          │
                                          ▼
                                   ШЛЮЗ ЭСКАЛАЦИИ
                                          │
                    ┌─────────────────────┴─────────────────────┐
                    ▼                                           ▼
            GEMINI-FAST ROUTER                         GEMINI-THINKING ROUTER
  (Микро-подсказка: <= 300 симв. JSON)       (Сложные формулы / Research: <= 1000 симв.)
```

### 2.1. Иерархия уровней тяжести (Tier Escalation)
* **TIER_0 (Детерминированный барьер — почти 0% CPU):** AST-парсинг, regex, валидация JSON-схем, линтеры (`ruff`, `mypy`), песочница путей (`path_sandbox`), лимит патча ($\le 30$ строк). Выполняется всегда первым без исключений.
* **TIER_1 (Быстрая локальная модель):** Первичный отсев явных логических противоречий.
* **TIER_2 (Полноценный состязательный консилиум):** Параллельная работа `Auditor-Rules` и `Auditor-Defense`.
* **TIER_3A (Gemini-Fast):** Вызывается только при подтвержденном локальном тупике (спор $>2$ раз). Строгий лимит пакета $\le 300$ символов.
* **TIER_3B (Gemini-Thinking):** Вызывается исключительно для изначально помеченных задач глубокого синтеза (`COMPUTE_INTENSIVE` — высшая математика, проектирование топологии, алгоритмическая оптимизация $O(N)$).

### 2.2. Принцип разделения вычислений и рассуждений (3D & Heavy Tasks)
* **Тяжелые вычисления (Compute):** Булевы операции, расчет полигональной сетки (mesh), коллизии, физика, симуляция, рендер $\to$ **всегда локальный GPU/CPU**. Запрещено тратить облачные токены на то, что считает процессор.
* **Рассуждения (Reasoning):** Определение стратегии геометрии $\to$ локальная модель. Только при тупике $\to$ микро-запрос к Gemini.

## 3. Архитектура локального состязательного консилиума (Multi-Agent Verification)

```text
                     ┌──────────────────┐
    Задача  ────────►│  LOCAL WORKER    │ (Генерирует гипотезу / diff <= 30 строк)
                     └────────┬─────────┘
                              │ результат
                              ▼
          ┌────────────────────────────────────────┐
          │      ПАРАЛЛЕЛЬНЫЙ СЛЕПОЙ АУДИТ         │
          │                                        │
          │  AUDITOR-RULES       AUDITOR-DEFENSE   │
          │  (Детерминированный  (Состязательный   │
          │   чекер контрактов    LLM: ищет баги,  │
          │   и стоп-гейтов)      без anchoring)   │
          └───────┬────────────────────┬───────────┘
                  │                    │
                  └──────────┬─────────┘
                             ▼
                    ┌──────────────────┐
                    │    АРБИТРАЖ      │ ── Оба PASS? ──► Фиксация в Golden
                    │  (Детерминир.)   │
                    └────────┬─────────┘
                             │ Спор / Тупик > 2 раз
                             ▼
                    ┌──────────────────┐
                    │  ШЛЮЗ ЭСКАЛАЦИИ  │ (Формирование JSON <= 300 симв.)
                    └────────┬─────────┘
                             │
                             ▼
                    ┌──────────────────┐
                    │  GEMINI ROUTER   │ (Роль: Наставник / Формула, НЕ код)
                    └────────┬─────────┘
                             │
                             ▼
                    Worker применяет совет
                             │
                             ▼
          Обязательный повторный аудит (Rules + Defense)
                             │
            ┌────────────────┴────────────────┐
            ▼                                 ▼
      Успех (PASS)                      Сбой (FAIL)
   Сохранение решения               Принудительный СТОП
  как GUIDANCE-XXXX в БЗ             Fail-Closed: revert
(система самообучается)             Статус: UNRESOLVED
```

### 3.1. Шесть механизмов надежности консилиума:
1. **Структурная гетерогенность аудиторов:** `Auditor-Rules` опирается на детерминированные чекеры и спецификации; `Auditor-Defense` — состязательный агент с установкой найти критический баг (Blind Review без предвзятости).
2. **Объективная уверенность вместо самооценки:** Модели запрещено оценивать собственную уверенность в процентах. Уверенность измеряется объективным сигналом: расхождением вердиктов и счетчиком итераций.
3. **Защита от «сговора по лени» (Review Fatigue):** Периодическое внедрение скрытых мутационных canary-тестов (заведомо дефектных фрагментов). Пропуск дефекта бракует аудитора.
4. **Асимметричный арбитраж:** 
   * `FAIL` от `Auditor-Rules` $\to$ безусловный блокирующий отказ.
   * `FAIL` от `Auditor-Defense` $\to$ предупреждение с обязательной оценкой рисков.
5. **Обучаемость на подсказках (`GUIDANCE-XXXX`):** Успешные советы Gemini индексируются локально в кэш паттернов. При повторении ошибки система применяет локальный рецепт, не обращаясь в облако повторно.
6. **Адаптивные пороги гейтов:** Учет статистики сбоев в `failure_index.json` во времени: для модулей с частыми регрессиями порог строгости проверок автоматически повышается.

## 4. Спецификация микро-пакета эскалации (Data Minimization)

* **Стандарт:** JSON по схеме `schemas/escalation_packet.json`.
* **Абсолютный потолок длины:** $\le 300$ символов на весь сериализованный JSON суммарно.
* **Структура полей:**
  * `g` (*goal*): суть шага телеграфным стилем (до 50 симв.).
  * `c` (*code*): только проблемный фрагмент 1–2 строки (до 100 симв.).
  * `e` (*error*): тип и место ошибки без трейса (до 60 симв.).
  * `w` (*want*): микро-сигнатура и ключевой инвариант (до 50 симв.).
* **Лимит обращений:** максимум 2 попытки. При повторном отказе — принудительный Fail-Closed.
